The window length decides which faults you can see, and how soon: long windows are dense but dilute a short burst; short windows react fast but are mostly zeros

A device's parsed log is cut into windows of length W, moved forward by a step; each window becomes a count vector with one entry per template (note B2). Here one rare template is watched. Normally it occurs at a low rate; during a fault burst it occurs much more often. A window is flagged if its count is unusually high for a normal window. The fleet rates, burst and alarm budget are illustrative; counts follow a Poisson model (my modelling choice, not from the notes).

Every constant is loaded from the inlined params block (also shipped as params.json), copied from ../constants.json. public = cited; illustrative = a round teaching number. The burst rates, the alarm budget and the 1/rank template mix are page inputs (illustrative). Detection delay uses an expected-count rule: the burst must have run long enough inside one window that the window's expected count reaches k*, plus a mean wait of half a step for the next window to close (my estimate).
