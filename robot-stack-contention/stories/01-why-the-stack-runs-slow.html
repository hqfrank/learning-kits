Robot stack contention · story 1 · an Orin-class 12-core board

Everything is slower when the whole stack runs, and each service has its own reason.

Think of the board as one kitchen that cooks for about {{stack_services}} services at once (illustrative). Each station slows down for a different reason. Two of the biggest full-stack numbers came from our own bench and a logging bug, not the board.

Where the kitchen breaks

  • A scheduler does not give a ticket to a named cook: any free pool core runs any runnable thread. And summed wait of threads that run in parallel is not added latency.
  • The oven is not one tray: the GPU has {{sm_count_orin}} SMs (sibling kit). Under time-slicing a context gets the whole GPU in its turn; MPS could let kernels of several processes share it, which the picture cannot show (B3).
  • The spice rack suggests one cause. For the motor-control services the path (cluster cache, board memory traffic, their own load) is not isolated.
  • The waiter does not "speak slowly": the cost is one log emit per item (stdout plus a /rosout publish), and CPU contention multiplies it.
  • The inspector did not misread: the request driver itself did not wait, so the full-stack number was measured correctly. It was caused by us.
