1Four checks before anyone picks up the radio

Most faults in remote control are at the edges, not in the model: an order delivered twice, two orders for one screen, a job that never reports. The front desk is cheap code that runs before any token is spent.

An order is running. A second, different order arrives. The device has one screen. What should the front desk do?

2One step, one hand, one report

The order is "open the video app and search for a title". The dispatcher does not plan it all. It plans one step, sends one hand, and waits for the report. Every turn comes back to the hub.

3The Spotter points at a photo, not at the panel

The Spotter never sees the panel live. It gets one shrunk photo, names a point in the photo's pixels, and device code must scale that point back. The two sizes have different shapes.

The photo is {{cu_reference_frame_recommended×}}. The panel is {{device_native_resolution_illustrative×}}. The photo was stretched to fit. The Spotter says "tap at ({{model_click_illustrative,}})". Where should the finger land?

The modelphoto point = panel point × scale, with x scale = photo width ÷ panel width and y scale = photo height ÷ panel height. Finger = photo point ÷ the scale the code uses. A plain resize stretches the image; the vendor advises keeping the aspect ratio, and either way you keep the scale factors and invert them for every returned point (04).

A steady offset in one direction is almost always a scaling bug. Check the scaler before the prompt. 04

5Every radio call costs time and money

Cost and latency are calls × tokens per call. Each call re-sends the briefing, the history and a photo. Most of that is the same as last time.

6The screen can lie

The order is trusted. The screen is not — and most of what the hands read comes from the screen. Design so that a fooled hand can do little harm.

7One demo is a sample of one

Where the crew breaks

  • Nobody "lives" on the device. The dispatcher and both hands are calls to a model in the cloud; the device only takes photos and carries out taps and OS calls.
  • The crew has no memory of its own. Each turn is a fresh model call, fed from the shared state (task, history, latest photo, summaries).
  • The Spotter never watches live. It sees one shrunk photo per look, taken after a settle wait.
  • The front desk and the switch do not judge anything. They are plain code reading fields.
  • The Keyholder's keys open the OS, not the inside of apps. Searching inside an app still needs the screen.
