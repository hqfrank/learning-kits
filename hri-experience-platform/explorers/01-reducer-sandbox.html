A safety input stops the robot only because the kernel sees it before the story does

A toy kernel runs one toy experience, the wave experience of note B1 (greet → await_wave → wave). Every input goes into one ordered queue (safety, reset, operator, command outcomes and timers, then observations; B4). The kernel admits or rejects it, handles the classes it owns itself, and passes the rest to the experience's pure reducer, which returns a next local state and a list of effects. The kernel validates the effects, commits one snapshot, and only then dispatches (B3). Step through a stream and watch three columns: what the kernel owns (the envelope), what the experience owns (its local state), and what it asked for (its effects). Then switch off interception and see what a story with no rule for "safety" does.

An illustrative toy, not the real kernel. The gesture-wait timer and the cleanup deadline are illustrative design parameters from constants.json; how long each primitive runs is a page choice. The experience, its three primitives and its claims follow notes B1 and B3; the reply-to-speech rule is a page addition so that "visitor speaks" has an effect. The "off" toggles show a design the notes reject, to make the rule visible.
