Commit first, then dispatch with deterministic IDs: a lossy link costs retries and pauses, not double waves

Each accepted event makes the reducer emit a few effects. A naive dispatcher sends each effect as it is emitted, gives every retry a fresh ID and records state afterwards. The kernel validates every effect, derives command IDs deterministically, commits state and intent as one snapshot, and only then dispatches; an adapter that sees a repeated ID treats it as a no-op (B3; Kleppmann's "effectively once"; the transactional outbox). Move the link's latency and failure rate and count the visible seams: moments a visitor can see the join — a second wave, half an event, a stalled story, a long pause, an action the state says never happened.

An illustrative model, not a measurement. "Seam" is this page's word for a visible artefact; the notes do not count seams. The settle bounds and the cleanup deadline are illustrative design parameters from constants.json; the ack timeout, the split between lost requests and lost acknowledgements, the naive dispatcher's timings and the pause a visitor notices are page choices. Expected values are computed in closed form and checked against a seeded simulation.
